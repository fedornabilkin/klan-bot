# Установка и обновление бота

Бот устанавливается самостоятельно на VPS. Ему нужны Telegram-токен, общий секрет уже настроенного Klan API и адрес этого API. Исходники и установка frontend/backend для выкладки бота не требуются.

## 1. Подготовьте VPS

Скачайте [Deploy/setup-server.sh](../Deploy/setup-server.sh) из этого репозитория и выполните на сервере:

```sh
sudo bash setup-server.sh bot
```

На VPS уже должны быть пользователь `deploy` с доступом к Docker Engine и Docker Compose 2.30+. Установщик проверит эти условия и создаст отдельные каталоги бота, сеть `klan-production` и постоянный volume `klan-production-bot-state`. Он спросит токен, существующий общий секрет API и адрес API, затем сохранит настройки в `/opt/klan/bot/shared/runtime.env`. Повторный запуск сохраняет токен, секрет и данные; адрес API можно обновить в диалоге.

`BOT_BACKEND_SECRET` должен совпадать с `BOT_INTERNAL_SECRET` API; токен — с токеном API. При отдельной первой установке адрес API нужно ввести явно как origin без пути и завершающего `/`. Укажите `http://api:3001`, только если API доступен в той же Docker-сети под именем `api`. Повторный запуск предлагает сохранённый адрес; общая установка `all` использует этот локальный адрес автоматически.

Для API на другом сервере укажите его доверенный частный адрес или HTTPS origin, доступный из контейнера. Нужны `/api/health` и `/internal/telegram/updates`. Публичный nginx сайта закрывает `/internal`, поэтому URL frontend не подходит. Передавайте служебный секрет по защищённой частной сети или проверенному TLS-соединению.

До первого запуска остановите прежний worker с этим токеном и убедитесь, что Telegram webhook отключён. Один токен обслуживает один polling worker. Если бот уже работал, сначала [перенесите его offset](deployment-troubleshooting.md#первый-запуск-и-сохранённый-offset).

## 2. Подключите GitHub

На своём компьютере войдите в GitHub CLI (`gh auth login`) и выполните тот же установщик:

```sh
bash setup-server.sh github bot
```

Он настроит environment `production` и SSH-параметры именно репозитория бота. Для автоматических выпусков из `main` required reviewers и wait timer должны быть выключены. Токен и секрет API остаются на VPS; переносить их в GitHub для обычной установки не нужно.

Уже настроенные пять SSH secrets (`DEPLOY_HOST`, `DEPLOY_PORT`, `DEPLOY_USER`, `DEPLOY_SSH_KEY`, `DEPLOY_KNOWN_HOSTS`) продолжают работать. Непустой старый secret `PRODUCTION_ENV` имеет приоритет: он **целиком заменяет** серверные настройки для нового релиза. Если хотите использовать файл VPS, удалите этот override. Когда `PRODUCTION_ENV` отсутствует или пуст, копируется серверный файл. При отсутствии обоих источников выпуск останавливается до замены worker.

## 3. Выпустите бота

Push или merge в `main` автоматически запускает [Production](../.github/workflows/deploy.yml). Для первого или повторного выпуска откройте **Actions → Production → Run workflow → main**. Pull request выполняет только проверки.

Workflow проверяет приложение, собирает образ в GitHub и передаёт его digest на VPS. Перед запуском проверяются конфигурация, offset и доступность API. Старый worker останавливается до запуска нового; постоянный offset сохраняется. Каждый релиз хранит собственную приватную копию настроек, поэтому изменения серверного файла применяются при следующем выпуске.

Проверка процесса после запуска не доказывает доставку Telegram. Журналы, перенос offset, файловые права и команда отката описаны в [дополнительных операциях](deployment-troubleshooting.md).
