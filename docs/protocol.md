# Протокол доставки в API

`POST /internal/telegram/updates`

Заголовки: `Content-Type: application/json`, `Authorization: Bearer <BOT_BACKEND_SECRET>`.

Тело — Telegram Update с числовым `update_id` и исходным `message`. API проверяет поля, используемые для входа (`from`, `chat`, `text`), и отбрасывает остальные. Ответ об успешной обработке: `200 { "data": { "accepted": true } }`.

Маршрут предназначен для связи сервисов. Он недоступен без секрета, не использует браузерную cookie и отклоняет запросы с `Origin` или `Sec-Fetch-Site`. Публичный reverse proxy не должен публиковать `/internal/`. При связи через недоверенную сеть необходим HTTPS; HTTP допустим внутри защищённой сети сервисов или на localhost.

## Доставка и повторы

Worker хранит следующий offset в `BOT_STATE_FILE`. Он отправляет обновления последовательно и сохраняет `update_id + 1` только после подтверждения API. При сетевой ошибке, ответе без `accepted: true` или ошибке записи offset повтор начинается с неподтверждённого обновления. Редиректы не разрешены, чтобы заголовок с секретом не оказался у другого сервиса.

API объединяет параллельные запросы с одним `update_id` и помнит последние 2000 успешно обработанных ID в памяти. После перезапуска API повторная доставка возможна: атомарная обработка одноразового auth request не допускает повторного создания профиля или выдачи сессии. Telegram-ответ в редком случае потери подтверждения и перезапуска может повториться; доставка не обещает exactly-once для внешнего `sendMessage`.

Сбой Telegram/API вызывает повтор через 5 секунд. Остановка прерывает long polling и ожидание повтора. Повреждённый offset-файл останавливает запуск: worker не сбрасывает его автоматически, чтобы не потерять позицию.

## Локальная конфигурация

В рабочей папке `klan/bot` пример `BOT_STATE_FILE=../ops/runtime/bot/offset.json` сохраняет служебные данные за пределами репозитория. При отдельном клонировании задайте собственный внешний каталог. В production используйте сохраняемый volume, например `/var/lib/klan-bot/offset.json`.
